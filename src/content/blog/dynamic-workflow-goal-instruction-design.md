## はじめに

前編では、Dynamic workflow と `/goal` コマンドを組み合わせてスキルを検証・改善する**手順**を紹介しました。

本記事では、その手順をうまく回すために本当に重要な部分——**どのような指示を与えるか**——に焦点を当てます。

結局のところ、次の2つが明確であればあるほどよいです。

| フェーズ   | コマンド / 仕組み | 明確にすべきこと                 |
| ---------- | ----------------- | -------------------------------- |
| 検証・調査 | Dynamic workflow  | **どういう風な作業を実行するか** |
| 改善・収束 | `/goal` コマンド  | **実行を続ける条件はなにか**     |

**この記事の対象読者**

- 前編のワークフローを試したが、意図と違う動きをした方
- Dynamic workflow や `/goal` に何を書けばよいか迷っている方

**この記事でわかること**

- Dynamic workflow に渡す指示の設計指針（作業の定義）
- `/goal` に渡す完了条件の設計指針（終了条件の定義）
- 両者を組み合わせた指示例と、アンチパターン

**この記事で扱わないこと**

- Dynamic workflow / `/goal` の基本概念（→ 前編を参照）
- Skills の作成手順の詳細

## なぜ「指示の設計」が効くのか

<!-- TODO: 前編の追記（/goal ultracodeでスキルが改善するまで検証と改善を）からの気づきを書く -->

`ultracode` や `/goal` を付けるだけでは、エージェントは動きますが、**何をもって成功とするか**が曖昧なまま走り続けることがあります。

指示が曖昧だと起きること:

- Dynamic workflow が「調査」で止まり、検証レポートまで届かない
- `/goal` の完了判定がブレて、改善が足りないのに終了する（または逆に収束しない）

逆に、作業内容と完了条件が分離して書けていると、人間が途中経過を確認しやすく、再実行もしやすくなります。

## Dynamic workflow への指示——何を実行するか

Dynamic workflow は**並列で多角的に作業を走らせる**フェーズです。ここで書くべきは「いつ終わるか」ではなく、**どんな作業を、どの観点で、どんな成果物まで**やるかです。

### 書くべき要素

1. **対象** — 何を検証・調査するか（ファイル、スキル、リポジトリ全体など）
2. **観点** — どの切り口で見るか（正確性、一貫性、手順の遵守、網羅性など）
3. **成果物** — 最後に何を出すか（レポート、指摘リスト、再現手順など）
4. **制約** — 触ってはいけないもの、使うツール、言語など

### 指示テンプレート（案）

```bash
ultracode で [対象] を検証してください。

- 観点: [観点1] / [観点2] / ...
- 成果物: [レポート形式・含める項目]
- 制約: [読み取り専用、特定ディレクトリのみ、など]
```

### 良い例 / 悪い例

<!-- TODO: 前編の open-computer-use 検証をベースに具体例を書く -->

**悪い例**

```bash
ultracode でこのリポジトリを見てください。
```

**良い例**

```bash
ultracode でこのリポジトリ内の Agent Skills を検証してください。

- 観点: スキル作法の遵守 / CLI 操作手順の記載 / ファイル間の一貫性
- 成果物: 確認済みの指摘のみをまとめた日本語レポート（重大度付き）
- 制約: スキル本体は読み取りのみ。修正はこのフェーズでは行わない
```

### チェックリスト

- [ ] 「検証」「調査」「比較」など、**動詞**が具体的か
- [ ] 並列化の**観点**が列挙されているか
- [ ] このフェーズの**出口**（成果物）が一文で言えるか
- [ ] 改善や修正を**このフェーズでやらない**ことが明示されているか（`/goal` に任せる場合）

## `/goal` への指示——いつ終わるか

`/goal` は**完了条件が満たされるまで**実行を続けるフェーズです。ここで書くべきは「何を調査するか」ではなく、**何をもって完了とみなすか**です。

### 書くべき要素

1. **完了条件** — 満たすべき状態（受け入れ基準、指摘ゼロ、テスト通過など）
2. **対象** — 何を直す・改善するか（前フェーズの指摘リスト、特定ファイルなど）
3. **検証方法** — 完了判定に使う確認（再検証、lint、手動チェック項目など）
4. **スコープ** — 今回のゴールに含めないこと（過剰なリファクタの禁止など）

### 指示テンプレート（案）

```bash
/goal [完了条件]

- 対象: [改善対象]
- 検証: [完了時に行う確認]
- スコープ外: [やらないこと]
```

### 良い例 / 悪い例

**悪い例**

```bash
/goal 指摘された問題点を改善して欲しいです。
```

**良い例**

```bash
/goal 前回の検証レポートの「確認済み指摘」がすべて解消され、同じ観点での再検証で新規の重大指摘がゼロになるまで、修正と再検証を繰り返してください。

- 対象: 検証レポートに記載されたスキルファイル
- 検証: 修正後に同じ観点で再読し、指摘の再発がないことを確認する
- スコープ外: 指摘に含まれないリファクタや新機能追加は行わない
```

### チェックリスト

- [ ] 完了条件が**観測可能**か（「改善して」ではなく「指摘ゼロ」など）
- [ ] 前フェーズの**成果物**（レポート）を入力にしているか
- [ ] **再検証**までゴールに含めているか
- [ ] スコープ外が書かれ、際限のない拡張を防いでいるか

## 2フェーズをつなぐ指示設計

前編のワークフローを、指示の観点で整理すると次のようになります。

```mermaid
flowchart LR
  A["Dynamic workflow\n何を実行するか"] --> B["成果物\n指摘レポート"]
  B --> C["/goal\nいつ終わるか"]
  C --> D["完了\n条件達成"]
```

| フェーズ         | 問い         | 指示の核          |
| ---------------- | ------------ | ----------------- |
| Dynamic workflow | 何をする？   | 観点 × 成果物     |
| `/goal`          | いつ終わる？ | 完了条件 × 再検証 |

### 一連の指示例（スキル検証・改善）

**フェーズ1: Dynamic workflow**

```bash
ultracode でこのリポジトリ内の Agent Skills を検証してください。

- 観点: スキル作法 / CLI 記述の正確性 / ファイル間一貫性
- 成果物: 確認済み指摘のみの日本語レポート
- 制約: 修正は行わない
```

**フェーズ2: `/goal`**

```bash
/goal フェーズ1のレポートの確認済み指摘がすべて解消され、同観点の再検証で重大指摘がゼロになるまで改善してください。
```

### 前編の追記パターン

前編末尾では、次のように **Dynamic workflow と `/goal` を1行にまとめる** パターンも追記されています。

```bash
/goal ultracodeでスキルが改善するまで検証と改善を
```

この書き方は手軽ですが、**作業内容（観点・成果物）と完了条件（何をもって改善完了か）が1文に圧縮**されています。慣れてきたらこの形でもよいですが、初めて回すときや結果がブレたときは、本記事のように**フェーズを分けて明示**する方が再現しやすいです。

## まとめ

- **Dynamic workflow** には「どういう作業を実行するか」を書く（対象・観点・成果物・制約）
- **`/goal`** には「実行を続ける条件はなにか」を書く（完了条件・再検証・スコープ）
- 2つを混ぜず、**検証で止めてレポートを渡し、改善は完了条件付きで回す**と意図通りに収束しやすい
